## 5.1 Source code

### Structure
```text
MediCare.Web/        Presentation: Controllers, Views (Razor), Hubs (SignalR), Infrastructure (SMTP, Twilio,
                     file storage, PDF/Excel export, reminder job), Security, wwwroot (vitala.css, vitala.js, charts)
MediCare.Services/   Business logic: Implementations, Interfaces, DTOs, Notifications (Factory), Common (rules)
MediCare.Data/       Data access: Entities, Context, Repositories (Generic + Unit of Work), Migrations, Seed
MediCare.Tests/      xUnit unit and integration tests
```

### Coding standards and naming
- C# conventions: `PascalCase` for types and members, `_camelCase` private fields, `Async` suffix on async methods,
  interfaces prefixed with `I` (`IAppointmentService`), DTOs suffixed `Dto`.
- One responsibility per class: controllers only translate HTTP ↔ services; rules live in services; data access only
  through the Unit of Work.
- Services return `ServiceResult` (success / error message) instead of throwing for expected business errors; controllers
  show the message with `TempData["Success"|"Error"]`.
- Front end: every CSS class starts with `vt-` (no clashes with Bootstrap); JavaScript behaviour is opt-in through
  `data-vt-*` attributes; every view starts with a comment naming its endpoints and form fields.
- Comments explain *why* (rules, security decisions), not *what*.

### Modularity and reuse
- Shared Razor partials: `_Sidebar`, `_VtIcon`, `_VtAlerts`, `_VtStatusBadge`, `_VtDoctorSummary`, `_DocumentList`,
  `_DocumentUpload`, `_PasswordToggle`, `_GoogleSignIn`.
- Layouts: `_VitalaLayout` (base), `_AuthLayout` (auth screens), `_DashboardLayout` (workspace with sidebar).
- Generic repository for every entity; one `NotificationFactory` for every notification type.

### Security and error handling
- See *7.2 Technical Documentation → Security* (Identity, roles, anti-forgery, upload validation, open-redirect
  protection, secrets outside git).
- Validation on the server for every form (plus client-side validation on auth screens).
- External services (email, SMS, live push) never break the main action: failures are caught and logged.
- Production error page (`/Home/Error`) and HSTS outside Development.

## 5.2 Version control and collaboration

- **Branching strategy:** feature branches from `main` (`feature/…`, `fix/…`, `docs/…`), one pull request per feature;
  `main` is only changed through reviewed pull requests. Large changes were stacked (a PR on top of another) to keep each
  review small.
- **Pull requests** (all with a description of what changed, why, and how it was tested):

| PR | Content |
| :--- | :--- |
| #1, #2, #4, #6, #9 | Project setup, N-Tier architecture, EF Core schema, booking, rescheduling, medical records service |
| #3 | Vitala UI (Figma) for every screen |
| #5 | Restyled backend pages (doctors, booking, appointments, availability, prescriptions) |
| #7, #8 | Sign-up role fix; login return URL |
| #10 | Medical records UI, signed-in header, access-denied page |
| #11 | Login connected to every page (logged-in patient/doctor) |
| #12 | Password recovery, Google sign-in, doctor profile + admin approval, real dashboard |
| #13 | Removed out-of-scope features |
| #14 | Notifications (Factory + SignalR), 24-hour reminders, tests, CI, README |
| #15 | Admin analytics + PDF/Excel export, patient profile, documents, days off, specializations, dark mode |

- **Commit messages:** a short summary line, then the reason and the main changes.
- **CI/CD:** GitHub Actions builds and runs the 71 tests on every pull request; deployment to Azure App Service runs on
  `main` once the Azure secrets are configured (see the README).

## 5.3 Deployment and execution
- **README** (root): system requirements, installation, configuration (user-secrets), execution, dev accounts, testing,
  CI/CD and deployment.
- **Run locally:** `dotnet ef database update --project MediCare.Data --startup-project MediCare.Web`, then
  `dotnet run --project MediCare.Web --environment Development`.
- **Deployed version:** Azure App Service (link added to the README once the Azure subscription is active).
