## 6.1 API & Internal Service Endpoints Documentation

MediCare exposes MVC pages and form posts, two JSON endpoints for interactive components (`FullCalendar.js`, the booking time picker),
a JSON unread counter, and a real-time **SignalR** hub. Every POST requires an anti-forgery token.

| Endpoint | Layer / Component | Auth Role | Description & Payload Behavior |
| :--- | :--- | :--- | :--- |
| `GET /Doctors?specialty&name&location&date` | `DoctorsController` → `DoctorService` | Public | Approved doctors (`IsApproved = true`) filtered by specialty, name, clinic address and (optionally) a free time on `date`. |
| `GET /Appointments/AvailableTimes?doctorId&date` (JSON) | `AppointmentsController` → `AppointmentService` | `Patient` | Free 30-minute start times: weekly slots − days off − active bookings − past times. |
| `POST /Appointments/Book` | `AppointmentsController` → `AppointmentService.BookAsync` | `Patient` | Re-checks the time, saves the appointment as `Pending` (filtered unique index as the last guard), and notifies the doctor through `NotificationService` → `NotificationHub`. |
| `POST /DoctorAppointments/Confirm` · `/Reject` · `/Complete` · `/NoShow` | `DoctorAppointmentsController` → `AppointmentService` | `Doctor` (own appointments) | Updates the status and notifies the patient (in-app, live, and email for confirm/reject). |
| `GET /DoctorAppointments/Events` (JSON) | `DoctorAppointmentsController` | `Doctor` | Calendar events for FullCalendar, colored by status. |
| `POST /MyAppointments/Cancel` · `GET/POST /MyAppointments/Reschedule` | `MyAppointmentsController` → `AppointmentService` | `Patient` | Cancels or moves a future Pending/Confirmed appointment (back to `Pending`, new reminder) and notifies the doctor. |
| `POST /Admin/CancelAppointment` | `AdminController` → `AdminService` | `Admin` | Cancels any active appointment and notifies the patient and the doctor. |
| `WSS /hubs/notifications` (`NotificationHub`) | `MediCare.Web` (SignalR) | `Patient`, `Doctor` | Server → client event `notification { id, title, message, link, unreadCount }` for toasts and the unread badge. |
| `GET /Admin/Dashboard?from&to` · `/Admin/ExportPdf` · `/Admin/ExportExcel` | `AdminController` → `ReportService` / `ReportExporter` | `Admin` | Monthly appointments, revenue, popular doctors and specializations, status, gender and age groups — rendered with **Chart.js**, exported to **PDF** (QuestPDF) and **Excel** (ClosedXML). |
| `POST /Documents/Upload` · `GET /Documents/Download/{id}` | `DocumentsController` → `MedicalDocumentService` | `Patient` (upload); `Patient`, `Doctor` (view) | PDF/JPG/PNG ≤ 10 MB verified by content; files served only to the patient and doctors they booked with. |

## 6.2 Testing & Validation Plan

The testing strategy validates functional workflows, concurrency constraints, security boundaries, and UI/UX usability targets:

1. **Unit Testing (xUnit):**
   * `NotificationFactory` (right class, recipient, link and channels for every event) and `ReminderRules` (due only within the next 24 hours).
2. **Integration & Concurrency Testing (xUnit + EF Core on in-memory SQLite):**
   * The real services, `GenericRepository<T>` and `UnitOfWork` against a relational database: booking, **0 double bookings** for the same `(DoctorProfileId, AppointmentDate, StartTime)` (`NFR-03`), working hours and days off, confirm / cancel notifications, reminders sent exactly once, document upload rules and privacy, specializations, profile validation and notification preferences.
   * Role-Based Access Control (`FR-02`) and ownership checks (`FR-11`, `FR-12`) are also verified end-to-end against the running site with the development accounts.
   * **Result: 71 / 71 automated tests pass**, with zero open critical bugs (`NFR-08`).
3. **User Acceptance Testing (UAT) & Prototype Validation:**
   * Executed with **100% synthetic data** (`NFR-03`, `NFR-06`) on desktop and mobile widths (`NFR-07`), in light and dark mode.
   * Covers the 5 core tasks of the **UI/UX Prototype Validation Checklist** (find a doctor, book, manage schedule, review analytics, keyboard/WCAG 2.2 AA accessibility), plus a link crawl of 60 pages for all four roles (0 broken links).

## 6.3 Deployment Strategy

* **Hosting Environment:**
  * The application is hosted on **Microsoft Azure App Service** backed by **Azure SQL Database**, targeting $\ge 99.0\$% **availability** during evaluation (`NFR-04`, `NFR-09`). SignalR runs in the App Service; **Azure SignalR Service** can be added when scaling to several instances.
  * All sensitive settings (connection string, SMTP password, `Twilio` token, Google client secret) live in **user-secrets** locally and in **App Service configuration** in Azure — never in source code (`NFR-02`).
* **Continuous Integration & Deployment (CI/CD) Pipelines:**
  * All code changes are merged via reviewed **GitHub Pull Requests** following a feature-branch workflow.
  * The **GitHub Actions** workflow (`.github/workflows/ci.yml`) runs on every pull request and push to `main`: `dotnet restore`, `dotnet build` (Release), all tests, and test-result upload. On `main`, once the Azure variable/secret are configured, it publishes and deploys to Azure App Service. EF Core migrations are applied with `dotnet ef database update` against the Azure SQL connection string.
* **Scaling & Extensibility Considerations:**
  * **Application & Notification Scaling (`NFR-10`):** interface-based adapters (`IEmailService`, `ISmsSender`, `IRealtimeNotifier`, `IFileStorage`) let the same code log messages in development and use SMTP / Twilio / SignalR / disk storage in production; storage can move to Azure Blob Storage by adding one class.
  * **Database & Real-Time Scaling:** the normalized `3NF` schema grew from 5 to 11 application tables during implementation (`MedicalRecords`, `Notifications`, `PatientProfiles`, `MedicalDocuments`, `Specializations`, `DoctorTimeOffs`) without breaking existing relationships.
